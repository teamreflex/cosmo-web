# Auth — Better Auth

The web app uses Better Auth with Discord/Twitter OAuth. Config lives in `apps/web/src/lib/server/auth.server.ts`; the auth tables are hand-tuned in the drizzle schema files.

## Schema generation

`bunx @better-auth/cli generate` **clobbers** the hand-tuned auth schema (citext columns, custom indexes, the current relations API). When a plugin adds tables or columns: regenerate → `git restore` the schema file → transplant only the new tables and columns, re-adding FKs and `mode: "date"` timestamps by hand.

The admin plugin's columns are transplanted this way into `packages/database/src/auth.ts`: `user.role`, `banned`, `ban_reason`, `ban_expires` and `session.impersonated_by`. `role` is the `user_role` pg enum (`user`, `moderator`, `admin`), `NOT NULL DEFAULT 'user'`, so rows inserted outside Better Auth still get a valid role and the comma-joined multi-role form is rejected. The enum's values are declared in `@apollo/database` so it doesn't depend on `@apollo/auth`; they mirror `@apollo/auth`'s roles, and the staff seed writes a `Role` into the column, so a role missing from either side fails to compile.

`user.is_admin` is unused and is dropped in a follow-up release. Drizzle selects every column the TS schema declares on each session lookup, so remove `isAdmin` from the TS schema one release before the migration that drops the column; otherwise the image still serving during that deploy fails every authenticated request.

The same follow-up release drops the non-unique `cosmo_account_user_id_idx`, which `cosmo_account_user_id_unique_idx` covers.

## Staff roles and permissions

- `@apollo/auth` (`packages/auth`) holds the access-control `statement`, the `user`, `moderator` and `admin` roles, `can(role, permissions)`, `parseRole()` and `adminPluginOptions`. The statement is declared `as const`, so a misspelt resource or action fails to compile. Moderators hold the trade, chat, listing, feedback and report actions; admins hold everything, adding `user: ["ban", "set-role"]`, `site: ["manage"]` and `audit: ["read"]`. Its bun test checks every role against every action through both `can()` and the plugin's `userHasPermission`.
- The server registers `admin(adminPluginOptions)`, and the test builds its throwaway instance from the same object. Never set `adminUserIds`: it bypasses every permission check.
- Impersonation and session management are absent from the statement, so no role can impersonate and `/admin/revoke-user-sessions` (which needs `session: ["revoke"]`) is refused for everyone. Banning already deletes the user's sessions.
- Better Auth types the session's `user.role` as `string`. Narrow it with `parseRole()` wherever it arrives from Better Auth or jsonb; missing, unknown and comma-joined values become `user`. Rows read through Drizzle are already typed by the enum and need no narrowing.
- Server functions gate staff work with `staffMiddleware(permissions)` from `lib/server/middlewares.ts`. It chains `authenticatedMiddleware`, throws `ExpectedError("forbidden")` when the role lacks a permission, and adds `role` to the context. Staff don't need a COSMO link; chain `cosmoMiddleware` after it only when the function writes the caller's COSMO address, as `$updateCollectionMetadata` does.
- The role reaches the client only on the current-account payload (`GetAccount.role`), never on `PublicUser`: `toPublicUser` also shapes other people's profiles, so a role there would publish staff status. `useHasPermission()` (`hooks/use-has-permission.ts`) reads it from `currentAccountQuery` and returns a `hasPermission` check for the signed-in user, built on `can(role, permissions)`. The `/admin` layout's `beforeLoad` sends anyone without a staff role to `/` and returns `role` in the route context. Each admin page's `beforeLoad` calls `requireStaffPage(context.role, permissions)` (`components/admin/common.ts`) and sets `notFoundComponent: AdminNoAccess`, so a staff member whose role lacks the page's permission gets a localised "You don't have access to this page" state inside the admin shell, and the page's loader never runs. It throws `notFound()` rather than an error because SSR answers route errors with a 500; the page responds 404. The server functions behind the page still refuse with `forbidden` on their own.
- Staff ban and unban through `$banUser` and `$unbanUser` (`lib/functions/staff-users.ts`), gated by `staffMiddleware({ user: ["ban"] })`. They load the target and refuse with `ExpectedError` codes before calling `auth.api.banUser` or `unbanUser` with `getRequestHeaders()`, since the plugin's own refusals aren't expected errors. The plugin reads the caller's session from those headers and checks their role against `ac` again.
- `hooks.before` in `auth.server.ts` 404s every browser call to the plugin's `/admin/*` routes, including set-role and impersonation. It tests `ctx.request` alone, which only router calls carry, unlike the api-key block's `ctx.request || ctx.headers`: the server functions must pass headers, so a headers test would refuse them too.
- No endpoint changes roles yet. Roles come from the seed or SQL until role management adds a `$setRole`.
- A report on a staff member is hidden from them, whatever their role, so they never see who reported them; other staff handle it. `lib/server/reports.server.ts` leaves those reports out of the queue and the tab and sidebar counts in the database query, and the report detail and the resolve, dismiss and escalate actions refuse them with `report_about_you`, which the detail localises as "This report is about you, so other staff will handle it." A refused read writes no audit row, and sign-in and sign-out drop the client's cached staff data, so the next staff member on a tab can't read the previous one's reports from the cache. /admin/audit rows still link a report by id, but never name who filed it.

## Staff audit and user events

- `$banUser` and `$unbanUser` write a `staff_audit` row with `recordStaffAudit()` (`lib/server/staff-audit.server.ts`), then publish on the Redis `user-events` channel with `publishUserEvent()` (`lib/server/user-events.server.ts`). The channel name and the `UserEvent` union live in `@apollo/auth/events`, so subscribers share the contract. The plugin commits the ban or unban before the audit row is written, and the event is published only once the audit row has committed, so a Redis failure surfaces as a 500 after both have committed.
- A ban started from a report passes the report's id as `reportId`. When the id names a report on the banned user, `$banUser` links the `user:ban` audit row to it and resolves every open or escalated report on that user with `resolveUserReports()` (`lib/server/reports.server.ts`), which reuses the report actions' resolve transition and writes one `report:resolve` row per report, all in one transaction with the `user:ban` row. Bans without a `reportId` leave reports untouched.
- `recordStaffAudit()` takes a `DbOrTx`, so a server function can write the audit row in the same transaction as the change it records. Report reads (`report:read`) are deduplicated per staff member and report for 10 minutes, so they are recorded one at a time; every other entry is an `UndeduplicatedAuditEntry`, and an array of those is written in one insert (an empty array writes nothing).
- Besides reports and bans, `$createApiKey`, `$updateApiKey` and `$deleteApiKey` write `api-key:create`, `api-key:update` and `api-key:delete` rows (target type `api-key`), copying the key's name, owner and enabled state into the detail so the row still reads after the key is deleted. `$updateCollectionMetadata` writes `metadata:update` (target type `collection`, keyed by slug). `$transferCosmoAccount` writes `cosmo-account:transfer` (target type `cosmo-account`, keyed by address), copying the COSMO username and both user ids into the detail. The other `site: ["manage"]` actions (events, eras, bands, the collection editor, cache and the platform notice) aren't audited.
- `staff_audit.action` and `target_type` are `varchar` columns typed by `staffAuditActions` and `staffAuditTargetTypes` in `@apollo/database/web/types`, so a new action needs no migration. Add it to `UndeduplicatedAuditEntry` (a read that must be deduplicated gets its own entry type, like `ReportReadAuditEntry`, and its own check in `recordStaffAudit()`) and `toAuditRow()`, give it a tone in `audit-row.tsx` and a label in `lib/client/staff-audit.ts` (all four locales), and the /admin/audit Action filter lists it.

## Protected accounts and self-demotion

- `PROTECTED_EMAIL_DOMAINS` is an optional server variable: a comma-separated list of email domains, trimmed and matched case-insensitively and exactly, so `team-reflex.com` matches neither `evil-team-reflex.com` nor `sub.team-reflex.com` unless that domain is listed too. The env schema parses it into a set with `parseEmailDomains()`; unset or empty protects nobody.
- Nobody, admins included, can ban, unban or change the role of an account whose email is verified and on a listed domain (`isProtectedAccount()`). Only a verified email counts because email sign-up doesn't require verification, so anyone could otherwise register an address on a protected domain and become unbannable. Nobody can ban themselves or lower their own role; raising it or setting the same role is allowed.
- `userChangeRefusal()` in `@apollo/auth/guard` decides all of this (unit-tested in `packages/auth/tests/guard.test.ts`). `guardUserChange()` (`lib/server/staff-users.server.ts`) loads the target, applies it and throws the `user_not_found`, `deleted_user`, `protected_user`, `self_ban` or `self_demotion` `ExpectedError`, which `formatAuthError` localises. `$banUser` and `$unbanUser` call it before the plugin. Its `set-role` change and the self-demotion refusal have no caller until `$setRole` lands.
- `staffMiddleware` refuses callers without `user: ["ban"]` before the guard runs, so nobody without the permission can probe which accounts are protected.
- The report detail's target carries a `protected` flag computed on the server with `protectionFor()` (`@apollo/auth/guard`), so the domain list never reaches the client. Only callers holding `user: ["ban"]` get a value; everyone else gets null, so nobody without the permission learns which accounts are protected. The report detail shows Ban and Unban only when the flag is `false`, and for a protected target the action bar's heading says protected accounts can't be banned.
- Protection follows the account's current `email` and `email_verified`, and an OAuth sign-in can replace both. Discord and X are configured with `overrideUserInfoOnSignIn`, so every sign-in through an already-linked Discord or X account writes the provider's email and verification onto the user. With `allowDifferentEmails`, that email can differ from the stored one (X sends the username when the X account has no confirmed email), and the account then silently loses protection. Both behaviours are deliberate: protection stays verified-email-only, and sign-ins keep overwriting the email.

## Bans

- A ban deletes the user's sessions, and the plugin's `session.create.before` hook refuses new sign-ins with the `BANNED_USER` code, which `getAuthErrorMessage` localises. OAuth sign-ins by a banned user land on Better Auth's error page instead.
- The ban reason is staff-only. It is stored in `user.ban_reason` and the `user:ban` audit row's detail, and never reaches the banned user, who sees only the generic localised "This account has been banned" message. The Ban dialog's reason hint tells staff so.
- Ban lengths are lazy: `banned` stays true after `ban_expires` passes, until the next sign-in attempt clears it. Treat a ban as active only when `isBanActive()` (`@apollo/auth/guard`) holds: `banned` is true and `ban_expires` is null or in the future. That automatic unban writes no audit row and publishes no event.
- A ban with no `banExpiresIn` (or zero) is permanent, but the plugin then leaves `ban_expires` untouched, so a lapsed earlier ban's expiry would lift it at the next sign-in. `$banUser` clears `ban_expires` for permanent bans in the same transaction as the audit row, so the stored ban, the audit row and the published event agree.

## COSMO accounts

- A user links at most one COSMO account, and a COSMO account belongs to at most one user: `cosmo_account.address` is unique, and `cosmo_account_user_id_unique_idx` makes `user_id` unique too. The index is NULLS DISTINCT, so the many cached, unlinked rows don't collide. Users can't unlink a COSMO account.
- `linkAccount()` (`lib/server/cosmo-accounts.server.ts`) is an upsert on the address whose update only applies when the row's `user_id` is null or already the caller. An empty RETURNING means another user holds the address (`account_linked_elsewhere`), and a unique violation on `user_id` means the caller already has a link (`cosmo_already_linked`). The codes live in the `accounts` error domain (`lib/universal/errors/accounts.ts`).
- The link wizard checks twice. `$generateVerificationCode` refuses when the account is picked, before storing a code, if the caller is already linked or the picked address belongs to anyone else. It is advisory: it trusts the address the client sends, and it answers `account_linked_elsewhere` whoever the owner is, so it reveals no more than the profile's verified badge already shows. The checks in `$verifyCosmoBio` after the bio check are the authoritative ones, and the conditional upsert backstops races between them.
- An address whose owner has an active ban (`isBanActive()` from `@apollo/auth/guard`) is refused with `cosmo_account_banned`. Only `$verifyCosmoBio` returns it, after the bio check, so ban status is told only to someone who has proven control of the COSMO account; every other owner gets `account_linked_elsewhere`.
- `$verifyCosmoBio` links and imports the address's legacy lists in one transaction that first takes `FOR SHARE` on the caller's user row where `deleted_at` is null. The lock conflicts with account deletion's `FOR UPDATE` on that row, so a link can't interleave with a deletion and leave a link or freshly imported lists on a deleted row. A caller whose row is deleted gets `not_signed_in`. The import copies each legacy list, with its entries, under the lowest numbered slug from `-2` up that is free among the user's lists and the other copies (`numberLegacyListCopies()` in `lib/universal/lists.ts`). Legacy lists can share a slug, so suffixing alone would hit the `(user_id, slug)` unique index and roll the link back.
- Lock order: a transaction that locks both a user row and a `cosmo_account` row locks the user row first, and two user rows in id order. Two transactions taking the same locks in opposite orders deadlock, and Postgres aborts one with `40P01`.
- `getCosmoAddress(executor, userId)` is the only way to read a user's linked address. It returns `{ kind: "linked", address, username }` or `{ kind: "none" }`, and a deleted user keeps their link. The address keeps its stored case, because the client compares it with `===` against the profile's address; compare it against lowercase indexer rows with `isEqual()` or `addr()`. `cosmoMiddleware` puts `{ address, username }` on the context.
- Reads that deliberately bypass `getCosmoAddress`: joins that only show a username beside a user (list owners, list matches, the notifications join, report targets, the API key owner search, `/api/objekt-list/for-user`), reads keyed by address rather than by user (`fetchFullAccount`, `searchCosmoAccounts`, `fetchKnownAddresses`, `fetchKnownPolygonAddresses`, `$fetchPins`, the by-address and by-addresses APIs, the schedules outbox drain), and writes (`cacheAccounts`, the seeds).

## Moving a COSMO account

- Admins move a COSMO link between users from `/admin/accounts`, for someone who lost access to the account it was linked to. `$transferCosmoAccount`, its two searches, the page and its sidebar item are all gated on `COSMO_TRANSFER_PERMISSIONS` (`lib/universal/cosmo-transfer.ts`), which is `user: ["set-role"]`: moving a link changes who an address and its reputation belong to, which is account administration on the same admin-only tier as a role change, not the site content that `site: ["manage"]` covers.
- `cosmoTransferRefusal()` (`@apollo/auth/guard`, unit-tested) refuses a protected source (`cosmo_transfer_protected`), a deleted user on either side (`cosmo_transfer_deleted`) and an actively banned user on either side (`cosmo_transfer_banned`). Only the source is protected, because receiving a link takes nothing from an account. Moving off a banned account would evade the ban, and moving off a deleted one would break the deletion's promise that the address can't be linked again.
- `transferCosmoAccount()` (`lib/server/cosmo-transfer.server.ts`) follows the lock order: both user rows `FOR UPDATE` in id order, then the `cosmo_account` row `FOR UPDATE`. A missing target is `user_not_found`; a missing source, or an address no longer linked to the source the admin picked, is `cosmo_transfer_source_changed`. A target that already has a link is `cosmo_transfer_target_linked`, with the unique `user_id` index as the backstop.
- Only the link moves. Lists and binders stay with each user, and token pins and locked objekts stay on the address. Binder pins on the address are deleted in the same transaction, because they point at binders the old owner keeps, and the address's pin cache is cleared after commit.
- A move publishes nothing on `user-events`.

## Account deletion

- Deleting an account anonymises the user row instead of removing it. `user.deleted_at` marks a deleted user; it is a plain drizzle column, not a Better Auth additional field, so users can't set it.
- Better Auth's own `user.deleteUser` is off, so its `/delete-user` and `/delete-user/callback` endpoints refuse every request (404, or 401 to a caller without a session) and nothing hard-deletes a user or unlinks their COSMO account.
- Deletion is proved by email. `$requestAccountDeletion` (`lib/functions/account.ts`) stores a single-use token in `verification` (identifier `delete-account-<token>`, value the user id, 24 h expiry) and emails a link to `/auth/delete-account?token=`. That page deletes only when its button POSTs the token to `$deleteAccount`, so mail link scanners and restored tabs can't delete an account. Requests are limited to 3 an hour per user.
- The Account dialog's Delete dialog reads `$checkAccountDeletion` through `accountDeletionQuery` (`lib/queries/account.ts`) each time it opens and lists any blockers before offering to send the email; `removeViewerQueries()` clears that query on sign-in and sign-out. The landing page needs the token's owner signed in. Deleting ends every session, so the page then drops the cached account and viewer queries while keeping its done state on screen.
- An account whose email fails `z.email()` is refused with `account_deletion_no_email`, which asks the user to add an email first. These are X sign-ins without a confirmed email, which store the X username as the email (see Protected accounts).
- `deleteAccount()` (`lib/server/account-deletion.server.ts`) runs in one transaction: it locks the user row `FOR UPDATE`, runs `canDeleteAccount()` again, consumes the token, then calls `anonymiseAccount()`. A reused, expired or other user's token is refused with `account_deletion_link_invalid`.
- `anonymiseAccount()` deletes the user's sessions, credentials (`account` rows), API keys and the verification rows whose value is the user id (reset-password and deletion tokens); their own notifications and the `list_match` notifications other users received about them; their objekt lists and binders (entries and binder pins cascade); and, for the linked address, the remaining pins, locked objekts and legacy lists. It then scrubs the row and sets `deleted_at`. After commit, the address's pin cache and the user's `cosmo:verify` key are cleared.
- It keeps the user id, `created_at`, grid columns, collection mode, the ban fields, the COSMO link, reports, staff audit rows and contributor attribution. The row is never removed, so no foreign key's cascade runs: anonymising deletes that data itself, and staff with `staff_audit` rows can delete their accounts. The kept COSMO link means the address can't be linked to any other account afterwards.
- The scrubbed row has the email `deleted+<id>@invalid` (`tombstoneEmail()`), an empty name, no image, username, display username or socials, `email_verified` false and role `user`. The `user_deleted_scrubbed_chk` CHECK rejects any deleted row that isn't scrubbed that way, so a half-scrubbed or re-filled tombstone can't be written. `z.email()` rejects the tombstone, and Better Auth checks sign-in, sign-up and email changes with it, so nobody can sign in with it, register it or change their email to it.
- `databaseHooks.session.create.before` and `databaseHooks.account.create.before` in `auth.server.ts` refuse a session or a credential for a deleted user with the `ACCOUNT_DELETED` code, which `getAuthErrorMessage` localises. Deletion already removes every credential and session; the hooks backstop any sign-in method and any flow already underway, such as a Discord or X link started before the deletion and finished after it. Better Auth keeps that link's OAuth state in `verification` as JSON, so deletion's user-id delete misses it, and its callback creates the `account` row without checking for a session. `guardUserChange()` refuses ban, unban and set-role on a deleted user with the `deleted_user` `ExpectedError`, through `userChangeRefusal()`'s `deleted-user` refusal, which is checked before protection, self-ban and self-demotion.
- `canDeleteAccount()` runs each check in the `blockerChecks` list in `account-deletion.server.ts` in turn on the caller's executor. Each returns a `DeletionBlocker` or null, and deletion is refused while any returns one. A new check is appended to that list, and a new kind of blocker extends the `DeletionBlocker` union in `lib/universal/account-deletion.ts`. `$checkAccountDeletion`, `$requestAccountDeletion` and `$deleteAccount` return the blocked result rather than throwing, so the UI can list the blockers, and `$deleteAccount` checks before it consumes the token, so a blocked attempt leaves the link usable.
- Anything created with a counterparty, such as a trade, a listing claim or a direct offer, checks `deleted_at` for each user involved while holding `FOR SHARE` on their rows (in id order, per the lock-order rule), as linking does, so it can't interleave with a deletion's `FOR UPDATE`.
- A rebuild of the notifications table must update `deleteListMatchNotificationsFrom()` (`lib/server/objekts/lists.server.ts`), which anonymising calls; otherwise deletion breaks or leaves stale notifications.
- Code detects a deleted user by `deleted_at`, never by blank fields: a live user can have no username or socials too.
- A deleted user's profile, under their COSMO username, their address or any child path, answers 404 with a "Deleted user" state. `fetchFullAccount()` returns `{ status: "deleted" }` with nothing else, and the `/@{$username}` layout's `beforeLoad` throws `notFound()` through `ensureProfileTarget()` (`components/profile/common.ts`), so no child loader fetches the address's collection, pins or balances, and the layout's `notFoundComponent` reads the cached result to show the deleted state. The `beforeLoad` returns nothing, since its return value is merged into every child's context and serialized for SSR. `fetchProfileCard()` returns undefined, so `/api/og/profile/*` answers 404.
- `/api/og/profile/*` is cached at the CDN for 24 hours, so a card cached before the deletion can outlive it at the edge until it expires or is purged by hand.
- Staff surfaces show deleted users as "Deleted user": `staffUsername()` (`lib/server/staff-users.server.ts`) returns null for them and `fetchStaffUsernames()` leaves them out, so report reporters, resolvers and targets, audit actors and audit targets come out null. A deleted report target has no Ban or Unban, and the audit log's Staff filter lists a deleted staff member as "Deleted user" with an id prefix. Reporting a deleted user, creating an API key for one and the API key owner search treat them as not found.
- Pages built from COSMO and chain data (transfers, objekt serials, the progress leaderboard, gravity, COSMO user search) keep showing the COSMO username, which belongs to the COSMO account rather than the deleted Apollo account.

## API Keys (admin-administered)

- The `@better-auth/api-key` **server plugin mounts `/api/auth/api-key/*` for all logged-in users** — the client plugin is only typed sugar, omitting it protects nothing, and there is no built-in role gate. `hooks.before` in `auth.server.ts` therefore 404s the HTTP routes: `ctx.path?.startsWith("/api-key/") && (ctx.request || ctx.headers)`. Optional chaining on `ctx.path` is required — server-only endpoints have no path.
- Admin operations run in server fns gated by `staffMiddleware({ site: ["manage"] })`: **create** via `auth.api.createApiKey({ body: { userId, ... } })` with NO `headers` (passing headers flips to client mode and ignores `userId`); **list/update/delete** via direct Drizzle on the `apikey` table (the plugin's own endpoints are session-self-scoped). Create, update and delete each write a staff audit row; update and delete write it in the same transaction, while create writes it after the plugin has stored the key.
- Keep `@better-auth/api-key` in version lockstep with `better-auth`; both are pinned in the root catalog.
- `rateLimit: { enabled: false }` on the plugin is deliberate — the default (10 verifications/day per key) would silently break polling consumers of the public API routes.
- Public API routes authenticate via `verifyRequestApiKey` (`lib/server/api-key.server.ts`): reads `Authorization` (optional `Bearer` prefix) or `x-api-key`, then calls the server-only `auth.api.verifyApiKey` — which has no HTTP path, so it's unaffected by the route block.

## Testing

Better Auth refuses a POST that carries cookies unless its `Origin` header matches `trustedOrigins`, which holds only `baseUrl()` (from `VITE_BASE_URL`). curl calls to `/api/auth/*` with a cookie jar must send a matching `Origin` header: without one they fail with `MISSING_OR_NULL_ORIGIN`, and with another origin they fail with `INVALID_ORIGIN`.
