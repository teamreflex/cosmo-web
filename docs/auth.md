# Auth — Better Auth

The web app uses Better Auth with Discord/Twitter OAuth. Config lives in `apps/web/src/lib/server/auth.server.ts`; the auth tables are hand-tuned in the drizzle schema files.

## Schema generation

`bunx @better-auth/cli generate` **clobbers** the hand-tuned auth schema (citext columns, custom indexes, the current relations API). When a plugin adds tables or columns: regenerate → `git restore` the schema file → transplant only the new tables and columns, re-adding FKs and `mode: "date"` timestamps by hand.

The admin plugin's columns are transplanted this way into `packages/database/src/auth.ts`: `user.role`, `banned`, `ban_reason`, `ban_expires` and `session.impersonated_by`. `role` is the `user_role` pg enum (`user`, `moderator`, `admin`), `NOT NULL DEFAULT 'user'`, so rows inserted outside Better Auth still get a valid role and the comma-joined multi-role form is rejected. The enum's values are declared in `@apollo/database` so it doesn't depend on `@apollo/auth`; they mirror `@apollo/auth`'s roles, and the staff seed writes a `Role` into the column, so a role missing from either side fails to compile.

`user.is_admin` is unused and is dropped in a follow-up release. Drizzle selects every column the TS schema declares on each session lookup, so remove `isAdmin` from the TS schema one release before the migration that drops the column; otherwise the image still serving during that deploy fails every authenticated request.

The same follow-up release drops the non-unique `cosmo_account_user_id_idx`, which `cosmo_account_user_id_unique_idx` covers.

## Staff roles and permissions

- `@apollo/auth` (`packages/auth`) holds the access-control `statement`, the `user`, `moderator` and `admin` roles, `can(role, permissions)`, `parseRole()` and `adminPluginOptions`. The statement is declared `as const`, so a misspelt resource or action fails to compile. Moderators hold the trade, chat, listing, feedback and report actions; admins hold everything, adding `user: ["ban", "set-role"]`, `site: ["manage"]`, `audit: ["read"]` and `cosmo: ["history"]`. Its bun test checks every role against every action through both `can()` and the plugin's `userHasPermission`.
- The server registers `admin(adminPluginOptions)`, and the test builds its throwaway instance from the same object. Never set `adminUserIds`: it bypasses every permission check.
- Impersonation and session management are absent from the statement, so no role can impersonate and `/admin/revoke-user-sessions` (which needs `session: ["revoke"]`) is refused for everyone. Banning already deletes the user's sessions.
- Better Auth types the session's `user.role` as `string`. Narrow it with `parseRole()` wherever it arrives from Better Auth or jsonb; missing, unknown and comma-joined values become `user`. Rows read through Drizzle are already typed by the enum and need no narrowing.
- Server functions gate staff work with `staffMiddleware(permissions)` from `lib/server/middlewares.ts`. It chains `authenticatedMiddleware`, throws `ExpectedError("forbidden")` when the role lacks a permission, and adds `role` to the context. Staff don't need a COSMO link; chain `cosmoMiddleware` after it only when the function writes the caller's COSMO address, as `$updateCollectionMetadata` does.
- The role reaches the client only on the current-account payload (`GetAccount.role`), never on `PublicUser`: `toPublicUser` also shapes other people's profiles, so a role there would publish staff status. `useHasPermission()` (`hooks/use-has-permission.ts`) reads it from `currentAccountQuery` and returns a `hasPermission` check for the signed-in user, built on `can(role, permissions)`. The `/admin` layout's `beforeLoad` sends anyone without a staff role to `/` and returns `role` in the route context. Each admin page's `beforeLoad` calls `requireStaffPage(context.role, ...permissions)` (`components/admin/common.ts`), which lets in a role holding any one of the permission sets it is given, and sets `notFoundComponent: AdminNoAccess`, so a staff member whose role lacks the page's permission gets a localised "You don't have access to this page" state inside the admin shell, and the page's loader never runs. It throws `notFound()` rather than an error because SSR answers route errors with a 500; the page responds 404. The server functions behind the page still refuse with `forbidden` on their own.
- Staff ban and unban through `$banUser` and `$unbanUser` (`lib/functions/staff-users.ts`), gated by `staffMiddleware({ user: ["ban"] })`. They load the target and refuse with `ExpectedError` codes first. `$unbanUser` then calls `auth.api.unbanUser` with `getRequestHeaders()`, since the plugin's own refusals aren't expected errors; the plugin reads the caller's session from those headers and checks their role against `ac` again. `$banUser` writes the ban itself (see Bans), because it has to commit in one transaction with the trade sweep, and deletes the user's sessions through `internalAdapter.deleteUserSessions()` once that commits, which is all the plugin's ban does besides the checks `$banUser` has already made.
- `hooks.before` in `auth.server.ts` 404s every browser call to the plugin's `/admin/*` routes, including set-role and impersonation. It tests `ctx.request` alone, which only router calls carry, unlike the api-key block's `ctx.request || ctx.headers`: the server functions must pass headers, so a headers test would refuse them too.
- No endpoint changes roles yet. Roles come from the seed or SQL until role management adds a `$setRole`.
- A report on a staff member is hidden from them, whatever their role, so they never see who reported them; other staff handle it. `lib/server/reports.server.ts` leaves those reports out of the queue and the tab and sidebar counts in the database query, and the report detail and the resolve, dismiss and escalate actions refuse them with `report_about_you`, which the detail localises as "This report is about you, so other staff will handle it." A refused read writes no audit row, and sign-in and sign-out drop the client's cached staff data, so the next staff member on a tab can't read the previous one's reports from the cache. /admin/audit rows still link a report by id, but never name who filed it.
- A trade report is a dispute: a party opens one with `$openDispute` (`lib/functions/trades.ts`), which freezes the trade, and a ban files a `party_banned` one for each of the banned user's accepted trades. Disputes sit in the `/admin/reports` queue, counts and Dispute filter beside user reports, and their detail shows the trade's parties, frozen time left and transfers. Staff settle a dispute there by completing, cancelling or extending the trade (`lib/functions/staff-trades.ts`), which resolves every open or escalated report on it in the same transaction; the generic resolve and dismiss refuse it with `report_trade_dispute`, since a closed dispute would leave its trade frozen, and escalate still works. Each staff trade action carries the `reportId` it was taken from (null for a trade with no dispute), and `actOnTrade()` refuses it with `trade_status_changed` unless the locked trade is still under that report, so a stale detail can't settle a trade another moderator has since extended or that was disputed again. Extending is refused with `trade_party_banned` while either party's ban is active, because `trade-timers` skip a banned party's trade and it would never time out; staff complete or cancel those trades instead. Staff can't act on a trade they are a party to (`trade_own`), and `visibleTo()` hides its reports from them as for a report on themselves (escalate is refused with `report_about_you`). `$createReport` takes user targets only.

## Staff names

- Staff surfaces name a user by their COSMO username, because that is their public identity and their `/@{username}` profile. `staffUser()` (`lib/server/staff-users.server.ts`) returns a `StaffUser` (`lib/universal/staff-users.ts`): `{ kind: "cosmo" }` with the linked account's username, or `{ kind: "apollo" }` with the Apollo username (`apolloUsername()`: display username, then username, then name) for a user without a link. Load its row with the `staffUserFields` columns and `with`, which join the COSMO account, or with `fetchStaffUsers()` for a set of ids; a polymorphic target id, such as a report's or an audit row's, can't be joined relationally.
- `StaffUserName` (`components/admin/staff-user-name.tsx`) renders it: a COSMO name as `@name` linking to the profile, an Apollo name muted with a "No COSMO" tag, since the two namespaces can overlap. `link={false}` drops the profile link inside another link, such as a queue row, and in the Ban dialog's title. Text-only places (toasts, combobox labels) use `staffUserText()`, which drops the tag.
- Where a user's current COSMO account may not be the one a row describes, as with the link history's user, staff see the Apollo username and an id prefix instead.

## Staff audit and user events

- `$banUser` and `$unbanUser` write a `staff_audit` row with `recordStaffAudit()` (`lib/server/staff-audit.server.ts`), then publish on the Redis `user-events` channel with `publishUserEvent()` (`lib/server/user-events.server.ts`). The channel name and the `UserEvent` union live in `@apollo/auth/events`, so subscribers share the contract. A ban's audit row commits with the ban; the plugin commits an unban before its audit row is written. The event is published only once the audit row has committed, so a Redis failure surfaces as a 500 after both have committed.
- A ban started from a report passes the report's id as `reportId`. When the id names a report on the banned user, `$banUser` links the `user:ban` audit row to it and resolves every open or escalated report on that user with `resolveTargetReports()` (`lib/server/reports.server.ts`), which reuses the report actions' resolve transition and writes one `report:resolve` row per report, all in one transaction with the `user:ban` row. Bans without a `reportId` leave reports untouched.
- `recordStaffAudit()` takes a `DbOrTx`, so a server function can write the audit row in the same transaction as the change it records. Report reads (`report:read`) are deduplicated per staff member and report for 10 minutes, so they are recorded one at a time; every other entry is an `UndeduplicatedAuditEntry`, and an array of those is written in one insert (an empty array writes nothing).
- Staff holding `trade: ["read-any"]` open any trade they aren't a party to read-only at `/trade/$id`: `$fetchTrade` answers them with a staff viewer carrying the trade's dispute report, and the page shows both parties in the third person with no actions. A staff member who is a party sees the normal party view. Trade reads aren't audited.
- Besides reports and bans, `$createApiKey`, `$updateApiKey` and `$deleteApiKey` write `api-key:create`, `api-key:update` and `api-key:delete` rows (target type `api-key`), copying the key's name, owner and enabled state into the detail so the row still reads after the key is deleted. `$updateCollectionMetadata` writes `metadata:update` (target type `collection`, keyed by slug). `$staffCompleteTrade`, `$staffCancelTrade` and `$staffExtendTradeDeadline` write `trade:complete`, `trade:cancel` and `trade:extend` (target type `trade`, linked to the trade's open dispute report, if any); an extend clears the trade's `dispute_report_id` as it returns it to `accepted`, so a later cancel links no report, and stores the new deadline and the hours picked, and an extend that completes the trade is recorded as `trade:complete`. `$banUser` writes one `trade:dispute` row per trade its sweep disputes, linked to the report the ban filed for it. The other `site: ["manage"]` actions (events, eras, bands, the collection editor, cache and the platform notice) aren't audited.
- `staff_audit.action` and `target_type` are `varchar` columns typed by `staffAuditActions` and `staffAuditTargetTypes` in `@apollo/database/web/types`, so a new action needs no migration. Add it to `UndeduplicatedAuditEntry` (a read that must be deduplicated gets its own entry type, like `ReportReadAuditEntry`, and its own check in `recordStaffAudit()`) and `toAuditRow()`, give it a tone in `audit-row.tsx` and a label in `lib/client/staff-audit.ts` (all four locales), and the /admin/audit Action filter lists it.

## Protected accounts and self-demotion

- `PROTECTED_EMAIL_DOMAINS` is an optional server variable: a comma-separated list of email domains, trimmed and matched case-insensitively and exactly, so `team-reflex.com` matches neither `evil-team-reflex.com` nor `sub.team-reflex.com` unless that domain is listed too. The env schema parses it into a set with `parseEmailDomains()`; unset or empty protects nobody.
- Nobody, admins included, can ban, unban or change the role of an account whose email is verified and on a listed domain (`isProtectedAccount()`). Only a verified email counts because email sign-up doesn't require verification, so anyone could otherwise register an address on a protected domain and become unbannable. Nobody can ban themselves or lower their own role; raising it or setting the same role is allowed.
- `userChangeRefusal()` in `@apollo/auth/guard` decides all of this (unit-tested in `packages/auth/tests/guard.test.ts`). `guardUserChange()` (`lib/server/staff-users.server.ts`) loads the target, applies it and throws the `user_not_found`, `protected_user`, `self_ban` or `self_demotion` `ExpectedError`, which `formatAuthError` localises. `$banUser` and `$unbanUser` call it before the plugin. Its `set-role` change and the self-demotion refusal have no caller until `$setRole` lands.
- `staffMiddleware` refuses callers without `user: ["ban"]` before the guard runs, so nobody without the permission can probe which accounts are protected.
- The report detail's target carries a `protected` flag computed on the server with `protectionFor()` (`@apollo/auth/guard`), so the domain list never reaches the client. Only callers holding `user: ["ban"]` get a value; everyone else gets null, so nobody without the permission learns which accounts are protected. The report detail shows Ban and Unban only when the flag is `false`, and for a protected target the action bar's heading says protected accounts can't be banned.
- Protection follows the account's current `email` and `email_verified`, and an OAuth sign-in can replace both. Discord and X are configured with `overrideUserInfoOnSignIn`, so every sign-in through an already-linked Discord or X account writes the provider's email and verification onto the user. With `allowDifferentEmails`, that email can differ from the stored one (X sends the username when the X account has no confirmed email), and the account then silently loses protection. Both behaviours are deliberate: protection stays verified-email-only, and sign-ins keep overwriting the email.

## Bans

- A ban deletes the user's sessions, and the plugin's `session.create.before` hook refuses new sign-ins with the `BANNED_USER` code, which `getAuthErrorMessage` localises. OAuth sign-ins by a banned user land on Better Auth's error page instead. The sessions are deleted after the ban commits, so if that step fails the user stays signed in until staff ban them again.
- The ban reason is staff-only. It is stored in `user.ban_reason` and the `user:ban` audit row's detail, and never reaches the banned user, who sees only the generic localised "This account has been banned" message. The Ban dialog's reason hint tells staff so.
- Ban lengths are lazy: `banned` stays true after `ban_expires` passes, until the next sign-in attempt clears it. Treat a ban as active only when `isBanActive()` (`@apollo/auth/guard`) holds: `banned` is true and `ban_expires` is null or in the future. That automatic unban writes no audit row and publishes no event.
- `$banUser` bans the user and sweeps their trades and listings in one transaction, which also writes the `user:ban` row (`banAndSweep()` in `lib/server/staff-users.server.ts`), so a banned user never has an accepted trade outside staff hands. It first locks the user and every counterparty of their accepted trades `FOR NO KEY UPDATE` in one statement ordered by id, then writes `banned`, `ban_reason` and `ban_expires`. Each accepted trade gets a `party_banned` trade report filed by the banning staff member, with the ban reason as its note, and becomes `disputed` under it with a staff `disputed` event, a `trade_disputed` notification to the counterparty and a `trade:dispute` audit row, so its timer stops and neither side can be timed out or marked abandoned; staff then complete, cancel or extend it. Trades already disputed keep their party's report and are left alone. Only then are the user's open listings `removed` and their pending offers withdrawn or declined (`closeOpenOffers()`), with no `listing_closed` notification; claimed listings stay with their now-disputed trades. Disputing trades first keeps the lock order (trades before listings), so a listing that a concurrent cancel reopens has committed before the `status = 'open'` sweep reads it. When a banned poster's trade ends other than by completing, its listing is removed rather than reopened, by staff or by `trade-timers` alike. The ban dialog shows how many accepted and disputed trades the ban leaves on hold for staff, and that it removes their open listings and closes their pending offers.
- A ban with no length is permanent: `$banUser` writes `ban_expires` as null, so a lapsed earlier ban's expiry can't lift it at the next sign-in.

## COSMO accounts

- A user links at most one COSMO account, and a COSMO account belongs to at most one user: `cosmo_account.address` is unique, and `cosmo_account_user_id_unique_idx` makes `user_id` unique too. The index is NULLS DISTINCT, so the many cached, unlinked rows don't collide. Users can't unlink a COSMO account; deleting the account unlinks it (see Account deletion).
- `linkAccount()` (`lib/server/cosmo-accounts.server.ts`) is an upsert on the address whose update only applies when the row's `user_id` is null, and it records the link in the link history (see COSMO link history). An empty RETURNING means the address is held: by another user (`account_linked_elsewhere`) or by the caller after a concurrent link (`cosmo_already_linked`), which a read of the holder tells apart. A unique violation on `user_id` means the caller already has a link (`cosmo_already_linked`). The codes live in the `accounts` error domain (`lib/universal/errors/accounts.ts`).
- The link wizard checks twice. `$generateVerificationCode` refuses when the account is picked, before storing a code, if the caller is already linked or the picked address belongs to anyone else. It is advisory: it trusts the address the client sends, and it answers `account_linked_elsewhere` for any owner, banned or not, so it reveals no more than the profile's verified badge already shows. The checks in `$verifyCosmoBio` after the bio check are the authoritative ones, and the conditional upsert backstops races between them.
- Both checks ask `cosmoLinkRefusal()` (`@apollo/auth/guard`, unit-tested) about the address's owner. It answers `banned` for an owner with an active ban (`isBanActive()`) and `linked-elsewhere` for any other owner but the caller. Deletion unlinks the address, so a deleted user owns none.
- An address whose owner has an active ban is refused with `cosmo_account_banned`. Only `$verifyCosmoBio` returns it, after the bio check, so ban status is told only to someone who has proven control of the COSMO account; every other live owner gets `account_linked_elsewhere`.
- A link never moves between users. Someone who lost access to the Apollo account their COSMO account is linked to recovers it in two steps: staff delete the lost account, which unlinks the address (see Account deletion), and the user then links the address to their new account through the bio. The wizard shows only the refusal, without pointing anywhere for help. An address held by a banned account stays with it.
- After the bio check, `$verifyCosmoBio` hands the profile to `linkVerifiedAccount()` (`lib/server/cosmo-accounts.server.ts`), which links and imports the address's legacy lists in one transaction that first takes `FOR SHARE` on the caller's user row. The lock conflicts with account deletion's `FOR UPDATE` on that row, so a link can't interleave with a deletion and leave a link or freshly imported lists behind for a deleted user. A caller whose row is gone gets `not_signed_in`. The import copies each legacy list, with its entries, under the lowest numbered slug from `-2` up that is free among the user's lists and the other copies (`numberLegacyListCopies()` in `lib/universal/lists.ts`). Legacy lists can share a slug, so suffixing alone would hit the `(user_id, slug)` unique index and roll the link back. It takes the profile instead of fetching it, so a script run with `bun run env --` can drive the link and its refusals against a local database without a COSMO account.
- Lock order: a transaction that locks both a user row and a `cosmo_account` row locks the user row first, and two user rows in id order. Two transactions taking the same locks in opposite orders deadlock, and Postgres aborts one with `40P01`.
- `getCosmoAddress(executor, userId)` is the only way to read a user's linked address. It returns `{ kind: "linked", address, username }` or `{ kind: "none" }`. The address keeps its stored case, because the client compares it with `===` against the profile's address; compare it against lowercase indexer rows with `isEqual()` or `addr()`. `cosmoMiddleware` puts `{ address, username }` on the context.
- Reads that deliberately bypass `getCosmoAddress`: joins that only show a username beside a user (list owners, list matches, the bell's actor usernames in `$listNotifications`, the staff name joins, the API key owner search, `/api/objekt-list/for-user`), reads keyed by address rather than by user (`fetchFullAccount`, `searchCosmoAccounts`, `fetchKnownAddresses`, `fetchKnownPolygonAddresses`, `$fetchPins`, the by-address and by-addresses APIs, the schedules outbox drain), and writes (`cacheAccounts`, `purgeAccount()`'s unlink, which takes the address from its `UPDATE … RETURNING`, the seeds).

## COSMO link history

- `cosmo_link_audit` is an append-only history of COSMO links: one row per link or unlink, naming the `cosmo_account` row, the user, the event (`linked` or `unlinked`) and the reason (`verified` or `account-deleted`). It gives a trail from a COSMO account to every Apollo account that has linked it. `cosmo_account.user_id` stays the current link, and nothing reads the history to decide one.
- Every change to `cosmo_account.user_id` appends its rows through `recordCosmoLinkChanges()` (`lib/server/cosmo-accounts.server.ts`) in the transaction that makes it: `linkAccount()` (`linked`, `verified`) and `purgeAccount()` (`unlinked`, `account-deleted`). A new way to change a link adds a reason and appends its rows the same way. `cacheAccounts()` never touches `user_id`, and the staff seed links its member without a row.
- Rows are only ever inserted. `user_id` is a plain text id without a foreign key, so the rows outlive the accounts they name; `cosmo_account_id` keeps its foreign key. A CHECK constraint ties `verified` to `linked` and `account-deleted` to `unlinked`. History starts with the release that added the table, so links made before it have no row.
- Staff holding `cosmo: ["history"]`, an admin-only action, read it on `/admin/accounts` as a log like the staff audit log: every row newest first, 50 at a time, ordered by id because the rows one transaction writes share `created_at` (`fetchCosmoLinkHistory()` in `lib/server/cosmo-link-history.server.ts`). Its search, from 3 characters, keeps the rows whose COSMO username or address, or whose user's username, starts with it; a deleted user's row is gone, so their rows are found through the COSMO account. A deleted user shows as "Deleted user", and each row's user id prefix tells deleted accounts apart.

## Account deletion

- Deleting an account deletes the user row. Better Auth's own `user.deleteUser` is off, so its `/delete-user` and `/delete-user/callback` endpoints refuse every request (404, or 401 to a caller without a session); `$deleteAccount` is the only way to delete an account.
- `$deleteAccount` takes a `DeletionProof` (`deletionProofSchema` in `lib/universal/schema/account.ts`): `{ kind: "email", token }`, the token from the emailed link, or `{ kind: "fresh-session" }`, a recent sign-in, which only an account without a deliverable email may use.
- `$requestAccountDeletion` (`lib/functions/account.ts`) stores a single-use token in `verification` (identifier `delete-account-<token>`, value the user id, 24 h expiry) and emails a link to `/auth/delete-account?token=`. The same transaction locks the user's row `FOR UPDATE` and deletes their earlier deletion tokens, so only the newest email's link works, even when two requests overlap. The lock also orders the request against a deletion running at the same time. That page deletes only when its button POSTs the token to `$deleteAccount`, so mail link scanners and restored tabs can't delete an account. Requests are limited to 3 an hour per user.
- An account whose email fails `z.email()` (`hasDeliverableEmail()`) can't receive the link. These are X sign-ins without a confirmed email, which store the X username as the email (see Protected accounts). It proves the deletion with a session created within the last 10 minutes instead (`isFreshSession()`). Freshness counts from `session.created_at`, as Better Auth's own `freshAge` check does, so refreshing a session doesn't renew it. That Better Auth check is off (`freshAge: 0`) and plays no part here. `$requestAccountDeletion` refuses such an account with `account_deletion_no_email`, and an account with a deliverable email keeps the email flow only.
- The Account dialog's Delete dialog reads `$checkAccountDeletion` through `accountDeletionQuery` (`lib/queries/account.ts`) each time it opens, with `useSuspenseQuery` behind a boundary inside the dialog's content. The answer depends on the session's age, so it is never prefetched; suspense keeps it for at least a second, so only a reopen within that second reuses it. It answers with the blockers, or with the step the dialog offers (`deletionStep()` in `lib/universal/account-deletion.ts`): `send-email`, `delete` on a fresh session, or `sign-in-again`, which tells a stale session to sign out and back in first. `removeViewerQueries()` clears that query on sign-in and sign-out. The landing page needs the token's owner signed in. Deleting ends every session, so the landing page then drops the cached account and viewer queries while keeping its done state on screen, and the dialog's `delete` step toasts, sends the viewer home and drops them as signing out does.
- `deleteAccount()` (`lib/server/account-deletion.server.ts`) runs in one transaction: it locks the user row `FOR UPDATE`, refuses an actively banned user (`isBanActive()`) with `account_deletion_banned`, runs `canDeleteAccount()` again, checks the proof against the locked row's email and the session's age (`deletionProofRefusal()`), consumes an email proof's token, then calls `purgeAccount()`. A reused, expired, replaced or other user's token is refused with `account_deletion_link_invalid`. A fresh-session proof is refused with `account_deletion_email_required` for an account with a deliverable email and with `account_deletion_session_stale` once the session is 10 minutes old, which the dialog answers with its `sign-in-again` state.
- Deleting frees the COSMO account for a new link, so a banned user who could delete would carry the address to a fresh account. The ban check runs under the row lock, which the admin plugin's ban `UPDATE` waits on, so a ban that lands after the email went out, or after a fresh sign-in, still refuses the deletion; the landing page then replaces its button with that refusal. The request step has no ban check of its own: a ban deletes the user's sessions and refuses new ones, so a banned user can't reach it.
- `purgeAccount()` first unlinks the COSMO account, setting its `user_id` to null and appending an `unlinked` (`account-deleted`) link history row. `cosmo_account.user_id` has no foreign key, so this unlink is what frees the address. For the unlinked address it deletes the pins, locked objekts and legacy lists, which are keyed by address. It withdraws the user's open listings and the direct offers they sent, and declines those they received (`closeOpenOffers()` in `lib/server/trades.server.ts`), each with `ended_at` set. It deletes the verification rows whose value is the user id (reset-password and deletion tokens). It then deletes the user row, and the foreign keys do the rest. After commit, the address's pin cache and the user's `cosmo:verify` key are cleared.
- Every foreign key to `user.id` is `ON DELETE CASCADE` or `SET NULL`, so the delete can't fail on a leftover reference. Sessions, credentials (`account` rows), API keys, objekt lists, binders and the notifications they received or caused (`notifications.user_id` and `actor_id`) cascade, and list entries, binder entries and binder pins cascade from those. `reports.reporter_id` and `reports.resolved_by` become null. `staff_audit.staff_id` and `cosmo_link_audit.user_id` have no foreign key, so staff with audit rows can delete their accounts and the rows keep the deleted id. A new table that references a user picks one of those actions, or keeps a plain id when its rows must outlive the user (see `docs/database.md`, Append-only audit tables).
- The deleted user's email and username are free again, so signing up with the same email creates a new, unrelated account. The OAuth flows need no guard of their own: a Discord or X link started before the deletion and finished after it can't create an `account` row, because its foreign key refuses the missing user.
- The unlinked address can be linked to another Apollo account by whoever proves control of it through the bio again, and its link history keeps the trail back to the deleted account's id.
- `canDeleteAccount()` runs each check in the `blockerChecks` list in `account-deletion.server.ts` in turn on the caller's executor. Each returns a `DeletionBlocker` or null, and deletion is refused while any returns one. A new check is appended to that list, and a new kind of blocker extends the `DeletionBlocker` union in `lib/universal/account-deletion.ts`. `$checkAccountDeletion`, `$requestAccountDeletion` and `$deleteAccount` return the blocked result rather than throwing, so the UI can list the blockers, and `$deleteAccount` checks before it consumes the token, so a blocked attempt leaves the link usable.
- Trade writes lock user rows first, then read `cosmo_account`, then lock trade rows, then listing rows, each kind in id order, and refuse a user whose row is gone, as linking does, so they can't interleave with a deletion's `FOR UPDATE`. Trades and listings are never locked in one mixed statement, and several rows of one kind are locked by a single `ORDER BY id` select before their guarded updates, since a multi-row `UPDATE` locks in scan order. Posting, editing and withdrawing a listing take `FOR SHARE` on the poster's row. Anything created with a counterparty, such as a listing claim or a direct offer, locks both users' rows `FOR NO KEY UPDATE` in one statement ordered by id: `FOR SHARE` can't serialise one user's parallel claims, so a claim cap checked under it would race, while `FOR NO KEY UPDATE` still conflicts with deletion's `FOR UPDATE` and the ban `UPDATE`, and a single ordered statement can't deadlock against a crossed claim. Actions on an existing trade (`lib/server/trades/trade.server.ts`) lock both parties' rows `FOR SHARE` in one ordered statement (`lockParties()`), then the trade `FOR NO KEY UPDATE` (`lockTrade()`), then the listing it came from. The outbox drain and `trade-timers` in `apps/schedules` start at the drain cursor's row, then lock every user they will notify `FOR KEY SHARE` in one ordered statement, then trades, then listings. Locking users before listings is what keeps them from deadlocking with an account deletion, which locks the user `FOR UPDATE` and then updates their listings, while a notification insert takes `FOR KEY SHARE` on its recipient through the foreign key.
- The deleted user's former profile, `/@{cosmo username}`, is an unlinked COSMO profile like any other: the address's collection and balances, without the verified badge, socials or the Report button.
- `/api/og/profile/*` is cached at the CDN for 24 hours, so a card cached before the deletion, showing the deleted user's pins, can outlive it at the edge until it expires or is purged by hand.
- Staff surfaces show a user who is gone as "Deleted user": a reporter or resolver set to null, an audit actor, audit target or link history user whose id no longer matches a row, and a report target that no longer exists. `fetchStaffUsers()` leaves missing ids out of its map. A deleted report target has no Ban or Unban, and the audit log's Staff filter lists a deleted staff member as "Deleted user" with an id prefix. Reporting a deleted user, creating an API key for one and the API key owner search treat them as not found.
- Pages built from COSMO and chain data (transfers, objekt serials, the progress leaderboard, gravity, COSMO user search) keep showing the COSMO username, which belongs to the COSMO account rather than the deleted Apollo account.

## Display currency

- `user.currency` is the code prices are shown in. It is `NOT NULL DEFAULT 'USD'` (`DEFAULT_CURRENCY` in `lib/universal/schema/currency.ts`). Only the signed-in user's own payload carries it: `toCurrentUser()` adds it to `CurrentUser` for `$fetchCurrentAccount`, while `toPublicUser()` leaves it out of every other user's `PublicUser`, since it hints at the user's country. A supported code is USD (the base of every rate) or one with an `fx_rates` row on the newest date. `$updateSettings`, `$createObjektList` and `$updateObjektList` call `assertSupportedCurrency()` (`lib/server/objekts/fx.server.ts`), which throws the `unsupported_currency` `ExpectedError`. The two update functions only check a code that differs from the stored one, so a user or list whose code lost its rate can still save other changes. `CurrencySelect` (`components/misc/currency-select.tsx`) offers only supported codes, each labelled with its `Intl.DisplayNames` name in the current locale.
- The column is a Better Auth `additionalField` with `input: true`, but only `$updateSettings` may write it. Better Auth field validators must be synchronous, so the rate check can't live there, and `input: false` would make Better Auth refuse the field from server calls too. Instead the `server-only-currency` plugin in `auth.server.ts` deletes `currency` from the body of router calls (those carrying `ctx.request`) to `/update-user` and `/sign-up/email`, so `authClient.updateUser({ currency })` changes nothing, and a body holding only `currency` fails with "No fields to update". `$updateSettings` checks the code, then calls `auth.api.updateUser` with headers but no request, which the plugin lets through.
- The current-account payload carries the latest rate of the user's currency as `GetAccount.fxRateToUsd` (null when the code has no rate, which shows prices in USD). `useDisplayCurrency()` (`hooks/use-display-currency.ts`) turns it into a `formatUsd` formatter, and `useSaleConversionRate()` returns the viewer's currency with the rate that converts a sale list's prices into it: null when the list already uses the viewer's currency or its own rate is missing. Converted amounts are approximate, so `formatConvertedPrice()` (`lib/utils.ts`) drops minor units from 1,000 and uses the locale's compact notation from 1,000,000, with the whole value in a `title` and screen-reader text (`ApproxPrice`). The seller's own price keeps its decimals through `formatPrice()`. A sale list card's price band (`SalePriceOverlay`) shows the converted price with the seller's own price on a small line above it, inside the card, so converted and same-currency lists share the grid's row height. Its Floor pill marks a priced serial at its collection's market floor, which `fetchMarketStats()` (`lib/server/objekts/market.server.ts`) computes across every seller at the latest rates. Changing a sale list's currency doesn't convert its entry prices, and the edit dialog warns about that. Loaders that key a query on the viewer's currency read it through `displayCurrency(account)`, the pure half of the hook. `/market` cards show each collection's USD floor from the indexer's `collection_market_stats` (see `apps/indexer/CLAUDE.md`), converted like any other price, so a floor can trail a sale list edit by up to a minute. A price range typed in the viewer's currency reaches the server as USD floor bounds (`toFloorBounds()` in `lib/universal/market.ts`), widened by half the currency's smallest unit. The listings dialog prices each serial at the latest rates when it opens.

## API Keys (admin-administered)

- The `@better-auth/api-key` **server plugin mounts `/api/auth/api-key/*` for all logged-in users** — the client plugin is only typed sugar, omitting it protects nothing, and there is no built-in role gate. `hooks.before` in `auth.server.ts` therefore 404s the HTTP routes: `ctx.path?.startsWith("/api-key/") && (ctx.request || ctx.headers)`. Optional chaining on `ctx.path` is required — server-only endpoints have no path.
- Admin operations run in server fns gated by `staffMiddleware({ site: ["manage"] })`: **create** via `auth.api.createApiKey({ body: { userId, ... } })` with NO `headers` (passing headers flips to client mode and ignores `userId`); **list/update/delete** via direct Drizzle on the `apikey` table (the plugin's own endpoints are session-self-scoped). Create, update and delete each write a staff audit row; update and delete write it in the same transaction, while create writes it after the plugin has stored the key.
- Keep `@better-auth/api-key` in version lockstep with `better-auth`; both are pinned in the root catalog.
- `rateLimit: { enabled: false }` on the plugin is deliberate — the default (10 verifications/day per key) would silently break polling consumers of the public API routes.
- Public API routes authenticate via `verifyRequestApiKey` (`lib/server/api-key.server.ts`): reads `Authorization` (optional `Bearer` prefix) or `x-api-key`, then calls the server-only `auth.api.verifyApiKey` — which has no HTTP path, so it's unaffected by the route block.

## Testing

Better Auth refuses a POST that carries cookies unless its `Origin` header matches `trustedOrigins`, which holds only `baseUrl()` (from `VITE_BASE_URL`). curl calls to `/api/auth/*` with a cookie jar must send a matching `Origin` header: without one they fail with `MISSING_OR_NULL_ORIGIN`, and with another origin they fail with `INVALID_ORIGIN`.
